The agent loop in auto3

Two human gates. The agent proposes, you approve, nothing deploys on its own.

  1. Agent writes feature SQLValidated against a dev schema first — you only read SQL that already ran.
  2. Gate 1: you review the SQLMainly looking for leakage. Approved features get committed to features/; the merge triggers the rebuild.
  3. Agent tunes within a fixed search spaceA handful of hyperparameters, a list of candidate features. Stop after three rounds or when the delta is under 1%.
  4. Gate 2: you review the resultCurrent vs candidate on the same held-out split, metric delta, what changed, MLflow run link.
  5. You push; deployment runsApproval is a registry stage change, not bespoke plumbing.
  6. Measurement on new data feeds backAccuracy where ground truth exists, input drift where it doesn't yet. A drop restarts the loop.

How the stack fits together

Four names, four different layers. Reading downwards, each one runs on the one below it.

Your codeTransforms, notebooks, jobs
DatabricksManaged platform: Delta, Unity Catalog, MLflow, scheduling
SparkThe open-source engine that splits work across machines
AzureThe machines, storage, identity and secrets underneath
DockerA separate axis — packages your own services, not Spark

Databricks doesn't own data centres, so Azure Databricks means the platform running on Microsoft hardware with ADLS Gen2 for files and Entra ID for login. Docker sits outside that stack entirely: n8n and the extractor run in containers on your host and hand data to Azure storage.

Fabric is the alternative to the middle two — Microsoft's own Spark-and-Delta platform. That's why existing Fabric knowledge carries over: same engine, same file format, different wrapper around them.

Data model

Business data and model metadata are different problems. Splitting them was the fix to the single combined store in the first sketch.

SchemaHoldsWritten by
bronzeRaw arrivals, never editedIngest job
silverCleaned, typed, deduplicated on a business keyIngest job, via MERGE
goldFeatures, labels, predictions, daily metricsFeature and scoring jobs
MLflowRuns, parameters, metrics, model versionsTraining job — not a table you design

The join between the two halves is a run_id column on gold tables, so any prediction can be traced back to the model version and the data that produced it. Every prediction row also carries its model_version; without that, a drop in accuracy can't be attributed to anything.

Rename the modules for what they do rather than build order — ingest-mail, ingest-sources, feature-store, train, serve. In six weeks auto2 and data1 won't mean anything to you, and less to a reviewer.

Reference build: the iris daily loop

A throwaway version of the real loop, small enough to finish in an evening and shaped like the thing it rehearses.

OrderTaskDoes
1ingestAppends the day's batch to bronze, MERGEs into silver so a retried day can't double its rows
2scorePredicts with the champion alias, writes predictions and one accuracy row per day
3trainLogs a run to MLflow, registers a candidate, prints the delta — and stops

Scoring runs before training on purpose: the day's measurement should reflect the model that was actually serving, not one retrained on the same day's data. Promotion is a separate deliberate act — setting the champion alias to the candidate version, which is the gate, and which also gives rollback for free.

Use aliases rather than the old Staging and Production stages; the stages are deprecated, so older tutorials will send you the wrong way. Run the whole thing on Databricks Free Edition until the loop works, then rebuild on Azure — idle clusters eat a student credit fast.

Routing

SubjectGmail filter → labelFlow

expreport 2026-09from:kochakorn.th@gmail.com subject:expreport → expreportReport sent to a fixed address. Also accepts last30; an empty subject means this month. Parked for now.
  • Route keywords are one word, with no hyphens or spaces. Gmail splits expense-report into two words, so it would also match subject:expense.
  • "Re: expense" can trigger the flow again, so n8n checks that the first word of the subject exactly matches the route.
  • Shared status labels are processed, failed and duplicate. The trigger query is label:expense -label:processed has:attachment.

Email note handling

  • The subject carries the route and tags (#food @card). The body is a free-text note.
  • The body is cleaned: use the text/plain part, and strip signatures, "Sent from my iPhone" and quoted replies (normalize.py, with tests).
  • The note may set the category, purpose and tags. Amount, date and merchant come only from the photo. If the two conflict, trust the photo and set needs_review = true.
  • With several photos in one email, the same note applies to each. The key is message_id + attachment index.

Line items and product matching

The same product is printed differently at each store: shallots have one name on a REWE receipt and another at ALDI. This is entity resolution, the same master-data problem companies have with SAP material masters and supplier names. Extract every line item from prompt v1, because adding it later means re-extracting every stored receipt.

TableHolds
storeREWE, ALDI, …
receiptOne row per receipt: store, date, total, source ids
receipt_lineRaw item text as printed (never edited), quantity, price, unit
productThe canonical product, e.g. Schalotten
product_alias(store, cleaned raw name) → product, match_method, confidence, confirmed by
categoryProduct categories: vegetables, dairy, …
  1. CleanLetter case, abbreviations, and split weight and unit (500G, 1KG, ST) out of the name.
  2. Exact lookupIn product_alias.
  3. Fuzzy matchrapidfuzz, within the same store.
  4. Embedding similarityFor names that look very different.
  5. LLM suggests a productWith a confidence score.
  6. Low confidence → review queueA confirmed match becomes a new alias, so automatic coverage grows and LLM calls fall over time.

Metrics: automatic coverage %, precision on a hand-labelled set, and the share sent to review over time. Payoff: price per kg for the same product across stores and over time.

Input variability

Photos arrive rotated, skewed or blurry, and stores change their receipt layout. The pipeline has to notice when that happens instead of quietly writing wrong numbers.

RiskWhat happensHandlingWhen
RotationPhone photos carry rotation in EXIF, which some tools ignore; people also shoot sideways or upside downApply EXIF orientation first (Pillow ImageOps.exif_transpose), then detect remaining rotation (Tesseract OSD) and rotatev2
Angle, cropReceipt shot at a slant, with table and backgroundFind the receipt edges and apply a perspective transform (OpenCV), then cropv3
QualityBlur, glare, low light, faded thermal paper, crumpled paperBlur score (Laplacian variance) and brightness check before the LLM; below the threshold, reply "please retake" instead of guessingv3
Split or combinedA long receipt in two photos, or two receipts in one photoTotals check flags it; merge by message_id, or send to reviewv3
Layout changeA store changes its format, a new store appears, Pfand, Rabatt and return lines, card slips attachedVision LLM instead of templates or regex; validation rules: line items sum to the total, MwSt 7% / 19% reconciles, date is plausible; a failure goes to reviewv2
DriftAccuracy drops for one store without any errorTrack validation failure rate per store; a rise means the format changed. The ground-truth set holds receipts from each store, including rotated and blurry onesv3
Model changeThe provider updates the model and output changesPin the model version, version prompts and schema, re-run evaluate.py before any switchv2

Always keep the original photo in bronze or Drive. When a rule or prompt improves, old receipts can be re-processed. In the corporate build, failed receipts land in a quarantine table instead of silver.

Router design

  • Channel adapters (Gmail now; schedule and LINE later) turn every input into one task envelope: case_id · owner_id · route · channel · args · body_clean · attachments · locale.
  • case_id is a hash of message_id, so a retried trigger never creates a second case. Trigger query excludes the bot's own address to prevent reply loops.
  • Sender maps to an owner; unknown senders are dropped with no reply.
  • Route resolution: plus-address (bot+expense@, saved as phone contacts) → subject keyword → LLM classifier limited to the routes this owner is allowed. Below 0.8 confidence, reply with the help list.
  • Route registry (Postgres): route, workflow id, enabled, owners allowed, required input, data class, whether an external LLM may see it.
  • Every sub-workflow returns the same result: done, needs_input or failed, plus summary, links and files. Only the router replies.
  • Storage split by owner and data class: my finance, my private data, sister's business.

Running it for real

  • Publish the Google OAuth app to production, or it stops every 7 days.
  • Watchdog workflow every 30 minutes: an unprocessed email older than 30 minutes, or any failure, sends a phone alert.
  • Nightly pg_dump and n8n workflow export.
  • PC-hosted is fine for me (emails wait in Gmail while it sleeps). Move to a small VPS before my sister depends on it.
  • Forwarded emails are untrusted input: the LLM only returns routes and fields, never triggers actions.

Forecast model: money left this month

The ML part of the receipt project. Every day it forecasts the balance at month end and the chance each category goes over budget, then the weekly report says what to do about it. Full model card: model.md.

TargetsEnd-of-month balance as P10 / P50 / P90, spend over the next 7 days, P(over budget) per category
LabelsFree. They arrive at month end or after 7 days, so the loop needs no manual labelling
DataRevolut CSV (one row per transaction), receipt line items, budgets; about 2 years of history
PrivacyReal data stays local; a synthetic generator feeds the demo and CI
  • Small data on purpose. Behaviour changes, so older data can hurt. Compare training windows of 6, 12 and 24 months, weight recent data more, and restart the window after a changepoint.
  • Model ladder. Rule baseline → seasonal naive → exponential smoothing → quantile regression / GBM. Each step must beat the one before in a rolling-origin backtest.
  • Report in three layers. Trend up or down, forecast range, then allowed daily spend, what drove the change, and cheaper stores. The LLM only writes the text; every number is computed and checked before sending.
  • Iteration log. Every round goes to MLflow and a table in the README, which shows the model getting better step by step.
